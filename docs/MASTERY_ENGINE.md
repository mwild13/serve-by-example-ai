# Mastery Engine — Source of Truth

Read this before adding a field, a formula or a module list anywhere near training progress. It describes the engine as of the 2026-09-30 audit remediation (Phases 4–5, October 2026). Elo was retired in that work. Don't reintroduce it.

## Where the logic lives

The rules run **in Postgres**, inside `SECURITY DEFINER` functions that only the service role can execute. The TypeScript in `lib/mastery.ts` is a thin wrapper plus read-side helpers.

| Piece | Where | What it does |
|---|---|---|
| `record_attempt()` | `supabase/migrations/20261003b_retire_elo_and_elite_numbers.sql` (first version in `20261002_…`) | Records one Scenario Training (`descriptor`) or Arena (`roleplay`) attempt in a single transaction, with the mastery row locked |
| `recordAttempt()` | `lib/mastery.ts` | Calls `record_attempt()`; throws `AttemptIdConflictError` when an attempt id is reused for a different scenario |
| `mark_module_mastered()` | `20261002_…` | Quiz mastery write; called only by the quiz run functions |
| `advance_quiz_run()` | `20261020_question_engine.sql` | Saves one graded quiz answer and the run's new state, and masters the module when the run passes. Replaces `advance_verify_attempt()` from `20261002_…` |
| `award_sbe_elite()` | `20261003b_…` | Assigns the user's SBE Elite number once, from a sequence |
| `getMasteryProgress()`, `getReviewQueue()`, `syncMasteryToVenueStaff()` | `lib/mastery.ts` | Reads, and the only bridge into the manager-facing `venue_staff` rows |

Nothing else writes `scenario_mastery`. Clients can't write it at all (Phase 2 RLS lockdown).

## Attempt rules (`record_attempt`)

- **Score scale:** 0–25, clamped and rounded. Arena grades 0–100 and passes `score / 4`, plus its own `passed` flag.
- **Pass:** a score of 15 or more, unless the caller passes `passed`. Arena passes only at 75/100 or above.
- **Mastery level** (0–3) on each scenario row:
  - A pass adds to `consecutive_correct`. The first pass gives level ≥1, two in a row give ≥2, three in a row give level 3 (mastered).
  - A fail resets `consecutive_correct`, adds to `consecutive_fails`, and drops the level by one (never below 0).
- **Spam guard:** an attempt within 60 minutes of the row's `last_attempt_at` still counts towards attempts and score totals, but doesn't move the level or the streak counters. It also doesn't move `last_attempt_at`, so the window can't keep sliding.
- **Spaced repetition:**
  - After a pass, `next_review_at` = now + level² days (1, 4, then 9 days).
  - After a fail, the scenario is due for review straight away.
- **Bridge hint:** `isBridge` is true after 2 fails in a row. Desktop Scenario Training shows a fixed hint; difficulty doesn't change.
- **Confidence:** `high_confidence_incorrect` and `low_confidence_correct` counters feed the manager "confidence mismatch" signal.
- **Arena (`roleplay`, `scenario_index` 40):** a pass sets `is_mastered`. A later fail never clears it.
- **Live Guest** (Rich update, Phase 6) records a finished conversation on the same `roleplay` / 40 row of the guest's module, with the conversation id as the attempt id and `evaluation.kind = "live_guest"`. It grades 0 to 100, passes at 75 unless the guest brief's must-do was broken (a breach), and sends `score / 4`. So a Live Guest pass counts in the service score exactly as an Arena pass does. Engine: `lib/live-guest/engine.ts`; briefs: `lib/live-guest/guests.ts` (server-only).
- **Pro badge streak:** `profiles.current_correct_streak` and `best_correct_streak` are updated in the same transaction, for Scenario Training only and not when spam-guarded.
- **Archived rows** (soft-deleted by "reset progress") are treated as fresh and reactivated.

### Idempotency

- Every graded submission carries an `attemptId`, a UUID generated by the client. `lib/attempt-id.ts` reuses it on retry and renews it after a success.
- `record_attempt()` claims the id in `training_attempts` first. A repeated id returns the stored result with `replayed: true` and changes nothing.
- The routes (`/api/evaluate`, `/api/arena/evaluate`) check `findRecordedAttempt()` before grading. A retry gets back the stored feedback without a second OpenAI call.
- Old clients without an id still work; they just get no retry protection.

## Verify quiz (module mastery): the question engine

Rebuilt in the Rich update, Phase 2 (`docs/Rich Update/`).

- **Question bank** (`lib/question-bank.ts`, `server-only`):
  - Every module starts with its True/False statements from `lib/verify-questions.ts` (8 per module, 320 in all), with ids `s0`, `s1`...
  - Questions in the other formats live in `lib/questions/module-NN.ts`, one file per module, for all 40 modules: best line, multiple choice, put in order, spot the mistake, a number, and which glass. Review sheets come from the code: `npm run questions:review`.
  - Each question has a `concept` (the statement it tests), a `difficulty` (1 to 3) and a `reviewed` flag.
  - Only reviewed questions are asked. Picture questions (`which_glass`, or any question with an `image` brief) stay off until `PICTURE_QUESTIONS_ENABLED` is switched on in Phase 9.
  - Question ids are stored in live runs. Never reuse an id for a different question.
- **Flow:**
  - `POST /api/training/verify/start` plans a run (`planRun()` in `lib/verify-quiz.ts`), stores it in `verify_attempts.run_state` and returns the first question only, with options shuffled and no answer.
  - `POST /api/training/verify/answer` grades one answer (`answerFits()`, `gradeAnswer()`), works out the run's next state (`advanceRun()`, a pure function) and saves it with `advance_quiz_run()`. That function re-checks status, expiry and position under a row lock, and calls `mark_module_mastered()` when the run passes. The reply carries the next question.
- **Planning a run:** one question per fact, so a fact is asked once unless it's missed. The first picks cover every format the module has. Up to 12 questions, easier ones first.
- **Pass rule:**
  - 6 right answers (`PASS_CORRECT`), in at least 3 formats (`PASS_FORMATS`), or in as many as the module has.
  - A question answered right never comes back. A wrong one brings back an unasked variant of the same fact 2 questions later, in another format when there is one. That fact must then be answered right before the run can pass.
  - The 3rd wrong answer ends the run (`MAX_MISSES`), and so does running out of questions. Both end as `exhausted`.
  - Every module has at least three live question types (checked by a test), so the full rule applies everywhere.
- **Test-out** (Rich update, Phase 5): `POST /api/training/verify/start` with `mode: "test_out"` plans a test-out (`planTestOut()`): up to 8 questions, no True/False, as many facts and formats as fit, hardest first. It passes on 6 right (`TEST_OUT_CORRECT`) and ends on the 2nd miss (`TEST_OUT_MAX_MISSES`). A miss brings no variant back. The goal carries `testOut: true`, and passing masters the module through the same `advance_quiz_run()` call. A test checks every module can run one. Offered from the Learn cards ("Know this already? Test out").
- **Starting difficulty from the skill check:** the placement check (`module_elo_baseline.category_scores`, 0 to 100 per category) is read when a normal run starts. Full marks in the module's category (`knowsArea()` in `lib/diagnostic-engine.ts`) orders that run hardest first. The pass rule doesn't change.
- **Mastered stays mastered.** The engine only ever sets mastery. Nothing in it clears a module someone has already passed.
- **Runs expire after 20 minutes** (server clock). Each answer is accepted once, at the position the server expects.
- **Rate limits:** 5 starts per module per 15 minutes, held in the database, plus per-isolate limits.
- **Answer key:** server code only. The `scenarios` table holds a copy of the True/False statements, but clients have no access to it (`20261003_lock_scenarios_answer_key.sql`).
- **After a pass,** `afterModuleMastered()` syncs the roster, stamps trial activation and checks SBE Elite.
- **Old engine:** `advance_verify_attempt()` and `verify_attempts.question_order` are no longer used. They are dropped in a later cleanup migration, once the new code has been live for a while.
- **Known limitation:** the quiz shows the correct answer after each question. That's a product choice, and it means a script can still learn the answers over a few runs, within the rate limits.

## Learn cards (before the quiz)

Added in the Rich update, Phase 4.

- **What:** each module opens with 4 to 6 short cards: a title, one rule, and why it matters. "Skip to quiz" is always there, and "Read the cards again" is offered after a failed run.
- **Where:** `lib/learn-cards.ts` (types and `loadLearnCards()`), with one file per module in `lib/learn-cards/module-NN.ts`. Each module's cards are a separate chunk, loaded only when the module opens. The screen is `components/quiz/LearnCards.tsx` (the `.lc` rules in `app/styles/staff.css`), used by `ModuleVerify.tsx` and the mobile `QuizScreen.tsx`.
- **Not server-only:** cards hold no answer key, so they can ship to the browser.
- **Each card's `concepts`** names the statements (`s0`..`s7`) it teaches. A test checks that every statement in a module is taught by at least one card, that a module has 4 to 6 cards, and that each card stays short.
- **Only reviewed cards are shown** (`reviewed: true`). A module with no reviewed cards opens straight on its quiz. Review sheets come from the code: `npm run cards:review`.
- **The quiz run starts after the cards,** so the 20-minute expiry doesn't run while someone reads.
- **Pictures** come in Phase 9. Cards work without them.

## SBE Elite

- **Earned with** verify quizzes passed for at least 80% of modules (`eliteThreshold()`), the same rule the badge shows in `lib/badges.ts`. Arena passes don't count.
- **Numbering:** `award_sbe_elite()` gives each user a number once, in the order people qualify.

## Manager roster sync (`syncMasteryToVenueStaff`)

- **Linking:** follows `venue_staff.staff_user_id` only, never email. Linking happens once, at sign-in, in `lib/staff-link.ts`.
- **Fields written:**

| `venue_staff` field | Meaning |
|---|---|
| `progress`, `module_mastery_pct` | Verify quizzes passed ÷ total modules |
| `service_score` | 80% quiz mastery + 20% Arena passes, each as a share of all modules |
| `product_score` | Share of technical-category modules mastered |
| `module_completion_pct` | Modules started at all ÷ total modules (fixed in Phase 5: it used to be capped at 10%) |
| `mastery_status` | `not-started` / `in-progress` / `mastered` |
| `high_confidence_incorrect_ratio` | Share of confidence-tagged misses that were high-confidence |

## Recommendations

`lib/module-navigator.ts` `getAvailableModules()` recommends 3 unmastered modules, ordered by:
1. Modules already in progress.
2. The weakest category from the placement check.
3. Lowest `difficulty_level`.
4. Lowest id.

The placement check (`/api/training/diagnostic/*`, scored in `lib/diagnostic-engine.ts`) stores per-category **percentages** in `module_elo_baseline`. The table name predates the Elo retirement. Only the order of the three categories is used, so older rows saved on the Elo scale still work. It asks six of the ten questions in `diagnostic_questions`, two per category; `PLACEMENT_QUESTION_KEYS` in `lib/diagnostic-engine.ts` sets which ones and their order.

Mobile "Continue Learning" (`HomeScreen.tsx`) picks the in-progress module with the lowest mastery, breaking ties by the one used most recently. If nothing is in progress, it picks the most basic untouched module.

## Canonical module catalog

The `modules` table (40 rows), read through `lib/module-navigator.ts` or `/api/training/modules`, is the source of truth for module metadata. Don't hardcode another module list.
