# Mastery Engine — Source of Truth

Read this before adding a field, a formula or a module list anywhere near training progress. It describes the engine as of the 2026-09-30 audit remediation (Phases 4–5, October 2026). Elo was retired in that work. Don't reintroduce it.

## Where the logic lives

The rules run **in Postgres**, inside `SECURITY DEFINER` functions that only the service role can execute. The TypeScript in `lib/mastery.ts` is a thin wrapper plus read-side helpers.

| Piece | Where | What it does |
|---|---|---|
| `record_attempt()` | `supabase/migrations/20261003b_retire_elo_and_elite_numbers.sql` (first version in `20261002_…`) | Records one Scenario Training (`descriptor`) or Arena (`roleplay`) attempt in a single transaction, with the mastery row locked |
| `recordAttempt()` | `lib/mastery.ts` | Calls `record_attempt()`; throws `AttemptIdConflictError` when an attempt id is reused for a different scenario |
| `mark_module_mastered()` | same migration as above | Quiz mastery write; called only by `advance_verify_attempt()` |
| `advance_verify_attempt()` | `20261002_atomic_attempts_and_verify_quiz.sql` | Records one graded quiz answer and masters the module when the streak is reached |
| `award_sbe_elite()` | `20261003b_…` | Assigns the user's SBE Elite number once, from a sequence |
| `getMasteryProgress()`, `getReviewQueue()`, `syncMasteryToVenueStaff()` | `lib/mastery.ts` | Reads, and the only bridge into the manager-facing `venue_staff` rows |

Nothing else writes `scenario_mastery`. Clients can't write it at all (Phase 2 RLS lockdown).

## Attempt rules (`record_attempt`)

- **Score scale:** 0–25, clamped and rounded. Arena grades 0–100 and passes `score / 4`, plus its own `passed` flag.
- **Pass:** a score of 15 or more, unless the caller passes `passed`. Arena passes only at 75/100 or above.
- **Mastery level** (0–3) on each scenario row:
  - A pass adds to `consecutive_correct`. The first pass gives level ≥1, two in a row give ≥2, three in a row give level 3 (mastered).
  - A fail resets `consecutive_correct`, adds to `consecutive_fails`, and drops the level by one (never below 0).
- **Spam guard:** an attempt within 60 minutes of the row's `last_attempt_at` still counts towards attempts and score totals, but doesn't move the level or the streak counters. It also doesn't move `last_attempt_at`, so the window can't keep sliding.
- **Spaced repetition:**
  - After a pass, `next_review_at` = now + level² days (1, 4, then 9 days).
  - After a fail, the scenario is due for review straight away.
- **Bridge hint:** `isBridge` is true after 2 fails in a row. Desktop Scenario Training shows a fixed hint; difficulty doesn't change.
- **Confidence:** `high_confidence_incorrect` and `low_confidence_correct` counters feed the manager "confidence mismatch" signal.
- **Arena (`roleplay`, `scenario_index` 40):** a pass sets `is_mastered`. A later fail never clears it.
- **Pro badge streak:** `profiles.current_correct_streak` and `best_correct_streak` are updated in the same transaction, for Scenario Training only and not when spam-guarded.
- **Archived rows** (soft-deleted by "reset progress") are treated as fresh and reactivated.

### Idempotency

- Every graded submission carries an `attemptId`, a UUID generated by the client. `lib/attempt-id.ts` reuses it on retry and renews it after a success.
- `record_attempt()` claims the id in `training_attempts` first. A repeated id returns the stored result with `replayed: true` and changes nothing.
- The routes (`/api/evaluate`, `/api/arena/evaluate`) check `findRecordedAttempt()` before grading. A retry gets back the stored feedback without a second OpenAI call.
- Old clients without an id still work; they just get no retry protection.

## Verify quiz (module mastery)

- **Flow:**
  - `POST /api/training/verify/start` creates a `verify_attempts` row with a shuffled question order (3 passes through the module's bank) and returns **prompts only**.
  - `POST /api/training/verify/answer` grades one answer against `lib/verify-questions.ts`, which is `server-only`, and calls `advance_verify_attempt()`.
- **Pass rule:** 5 correct in a row (`VERIFY_STREAK_REQUIRED` in `lib/verify-quiz.ts`). A wrong answer resets the streak. If the questions run out first, the run ends as `exhausted`.
- **The server keeps the streak.** Each answer is accepted once, at the position the server expects. Runs expire after 20 minutes (server clock).
- **Rate limits:** 5 starts per module per 15 minutes, held in the database, plus per-isolate limits.
- **Answer key:** exists only in server code. The `scenarios` table holds the same 320 questions, but clients have no access to it (`20261003_lock_scenarios_answer_key.sql`).
- **After a pass,** `afterModuleMastered()` syncs the roster, stamps trial activation and checks SBE Elite.
- **Known limitation:** the quiz shows the correct answer after each question. That's a product choice, and it means a script can still learn the answers over a few runs, within the rate limits.

## SBE Elite

- **Earned with** verify quizzes passed for at least 80% of modules (`eliteThreshold()`), the same rule the badge shows in `lib/badges.ts`. Arena passes don't count.
- **Numbering:** `award_sbe_elite()` gives each user a number once, in the order people qualify.

## Manager roster sync (`syncMasteryToVenueStaff`)

- **Linking:** follows `venue_staff.staff_user_id` only, never email. Linking happens once, at sign-in, in `lib/staff-link.ts`.
- **Fields written:**

| `venue_staff` field | Meaning |
|---|---|
| `progress`, `module_mastery_pct` | Verify quizzes passed ÷ total modules |
| `service_score` | 80% quiz mastery + 20% Arena passes, each as a share of all modules |
| `product_score` | Share of technical-category modules mastered |
| `module_completion_pct` | Modules started at all ÷ total modules (fixed in Phase 5: it used to be capped at 10%) |
| `mastery_status` | `not-started` / `in-progress` / `mastered` |
| `high_confidence_incorrect_ratio` | Share of confidence-tagged misses that were high-confidence |

## Recommendations

`lib/module-navigator.ts` `getAvailableModules()` recommends 3 unmastered modules, ordered by:
1. Modules already in progress.
2. The weakest category from the placement check.
3. Lowest `difficulty_level`.
4. Lowest id.

The placement check (`/api/training/diagnostic/*`, scored in `lib/diagnostic-engine.ts`) stores per-category **percentages** in `module_elo_baseline`. The table name predates the Elo retirement. Only the order of the three categories is used, so older rows saved on the Elo scale still work.

Mobile "Continue Learning" (`HomeScreen.tsx`) picks the in-progress module with the lowest mastery, breaking ties by the one used most recently. If nothing is in progress, it picks the most basic untouched module.

## Canonical module catalog

The `modules` table (40 rows), read through `lib/module-navigator.ts` or `/api/training/modules`, is the source of truth for module metadata. Don't hardcode another module list.
